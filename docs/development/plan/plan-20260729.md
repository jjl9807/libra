# 上游 Git 兼容测试迁移第一批计划（2026-07-29）

**模板版本:** 依据 `docs/development/plan/plan-template.md` `v2`（2026-07-28 生效）整份编写。本文「任务卡粒度规则（强制）」与「Verification 判定口径」两节转录自模板 v2；如与模板正文冲突，一律以模板为准。

## 文档职责

本文解决 `plan-long.md` 的 **CT-01（上游 Git 套件驱动的兼容性证据账本 / Grit Git 兼容测试迁移）** 的第一批可执行范围，目标是交付：合规与族级范围裁定、两项由分歧探测确证的 Git 兼容缺陷修复、一套带强制字段的兼容证据账本与其守卫，以及 t4（diff / format-patch）族首批场景从上游语料到 Libra 原生测试的 clean-room 迁移。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `libra config <key>` 裸读、`libra update-ref` 的 `<newvalue>`/`<oldvalue>` 操作数解析这两条 Git 兼容表面。
- 兼容证据账本的落点、schema、必填字段与 compat 守卫（`tests/compat-ledger/`、`tests/compat/compat_ledger_schema.rs`）。
- t4 族首批（≤ 12 个上游文件所含场景）的清单、四分类，以及其中 `direct` 场景重写为 Libra 原生 Rust 集成测试。
- Grit 相关的族级范围裁定文档、`D` 编号绑定，以及既有 Grit 文档债收口。
- 四个发布切片的版本递增、tag 推送与发布证据（ADR-CT-05）。

### 非目标

- **不 vendor 上游 GPLv2 语料**：不把 `t*.sh`、`test-lib*.sh`、`t/helper`、C helper 或其逐字预期输出复制/翻译进本仓库（ADR-CT-01）。
- **不建离线 gap 发现器**（其持久化模型按 `plan-long.md` CT-01：代码入库、上游语料不入库）：S2 阶段整体延后（DEFER-01），因其同时受 DEP-01 许可裁定与 DEP-02（SB-04 测试隔离基线）阻塞。`pass`/`fail`/`skip`/`xfail`/`timeout` 五分列统计口径随 S2 一并延后——clean-room 重写路径不产生这五种结果，只产生分类。
- **不做 t4 之外的族 wave**，也不在本计划内处理 t4 的 `adapted` 场景：移交后续日期计划（DEP-03、DEFER-02）。
- **不改 commit/tag 对象编码**（DEFER-03）、**不改 index 编码**（DEFER-04）、**不改外部 crate `git-internal`**（DEFER-05）。
- **不改 `.libra` 仓库模型**：不新增 `--git-dir`/`--work-tree`/`-C`，不做 `git → libra` 的 argv[0] 分派。
- **不引用 Grit 通过率作为目标或完成判据**（`plan-long.md`「不采纳未经限定的竞品指标」）。

### 成功定义

- `libra config <key>` 与 `git config <key>` 在已设置 key 上行为一致（stdout 为最后一个值、退出码 0），未设置时 exit 1 + `LBR-CLI-002`。
- `libra update-ref refs/heads/<name> <rev>` 接受**本身即 commit** 的 revision 表达式，`<ref>` 操作数的既有 `refs/heads/*` 收窄不变。
- 仓库内存在场景级兼容证据账本，其每条场景都带 `reason` / `category` / `owner` / `review_date`，并由已注册的 compat 守卫强制。
- t4 首批 `direct` 场景已作为 Libra 原生测试运行通过，且候选集可由已提交的命令流水线复算出同一结果。
- 全部非延后任务 `Lifecycle=done` 且 `Acceptance=complete`，Codex review 结论为 `PASS`。

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-CT-01: 迁移形态为 clean-room 场景重写，不 vendor 上游语料

- **Status:** Accepted
- **Context:** grit 的 `grit-git`、`/git`、`/tests` 是 GPLv2，Libra 是 MIT（`grit/LICENSE`、`Cargo.toml:5`）。`docs/development/gap/grit-gap.md:413` 已把「不得复制或翻译 GPLv2 来源的源码、shell harness、C helper、`t*.sh` 文本或其逐字预期输出」写成高风险质量门；`:93` 另行禁止把 grit 的 shell harness 作为 Libra 的测试接入形态。
- **Decision:** 「迁移」= 迁移**测试覆盖面**。归纳上游测试的场景、前置状态、操作步骤、断言与边界，用 `tests/command/*`、`tests/helpers/`、`tests/harness/` 的既有 Libra 写法重写；断言写 Libra 的实测预期。允许保留的只有短小数据型 fixture，且必须记录来源 tag/commit、许可证与不能由 Libra helper 生成的理由。
- **Alternatives considered:** ①整体 vendor `t*.sh` + 移植 harness——被许可证与既有决策否决；②仓库外运行上游语料作 gap 发现器——「仅运行而不分发」是否合规无裁定（DEP-01），且探针违反尚未落地的 SB-04 隔离要求（DEP-02），整体延后为 DEFER-01。
- **Consequences:** 迁移吞吐较低但可 review、可维护、无许可风险；覆盖面完整性依赖清单卡，因此账本（CT2-01）是必需品。
- **Revisit when:** DEP-01 给出明确裁定且 SB-04 已落地。

### ADR-CT-02: 初始分支名走既有 `init.defaultBranch`，不新增 `GIT_TEST_*` 环境变量读取

- **Status:** Accepted
- **Context:** 上游套件用 `GIT_TEST_DEFAULT_INITIAL_BRANCH_NAME` 统一初始分支名。现状核对显示 Libra 已支持 `init.defaultBranch` 级联与 `-b/--initial-branch`（`src/command/init.rs:250-263`（`-b` 短选项声明）与 `:496-521`（级联解析）、`COMPATIBILITY.md:103`）。
- **Decision:** 不在生产代码中读取任何 `GIT_TEST_*` 变量。迁移后的测试通过 `libra init -b <name>` 或预置 `init.defaultBranch` 达成同一效果。
- **Alternatives considered:** 读取该变量——会把上游测试专用变量固化进生产语义，并与 `init.defaultBranch` 形成第二个事实源，违反 GC-02。
- **Consequences:** `plan-long.md` CT-01 的 S1 候选项列表需订正（CT0-01 承接）。
- **Revisit when:** 出现必须在生产路径识别上游测试环境的需求（当前无）。

### ADR-CT-03: 兼容证据账本的落点、粒度与格式

- **Status:** Accepted
- **Context:** `docs/development/commands/_compatibility.md:93` 记录了一次已执行的反向决策——删除参数级 YAML 及其 `test_evidence` / `last_verified` 字段。`plan-long.md` 要求排除项必带 `reason`/`category`/`owner`/`review date`，且账本以**场景**为行。`tests/compat/matrix_alignment.rs:295-298` 禁止新建顶层 `scripts/`。
- **Decision:** 账本落在 `tests/compat-ledger/<family>/<stem>.toml`，**一个上游源文件一个 TOML，文件内以 `[[scenario]]` 数组承载多条场景行**；场景 ID 为 `<stem>::<upstream_test_name_slug>`，稳定且与上游测试标题一一对应。每条 `[[scenario]]` 必填 `id`、`category`（闭集 `direct`/`adapted`/`declined`/`blocked`）、`reason`、`owner`、`review_date`（ISO 8601 日期）、`upstream_revision`（40 位 hex 的 pinned grit SHA）、`upstream_file`（源脚本文件名）、`libra_command`（对应 Libra 命令）、`libra_surface`（对应 flag / 子面）；`declined` 另必填 `decision_id`（`D<n>` 或具名 `D-*`），`blocked` 另必填 `blocked_by`。`libra_tests` **不是 schema 级必填字段**（分类阶段尚无测试函数名），其完备性由 CT3-02 的收口守卫单独强制：wave 收口时每条仍为 `direct` 的场景都必须有非空 `libra_tests`。账本**不**复制 `COMPATIBILITY.md` 的 tier，也不承载参数级 `test_evidence`。运行结果统计（`pass`/`fail`/`skip`/`xfail`/`timeout`）不属于本 schema——clean-room 重写只产生分类，统计随 DEFER-01 的离线发现器一并定义。
- **Alternatives considered:** ①一个源文件一行——与 `plan-long.md` 的场景级要求冲突，且同一脚本内常有混合分类；②写进 `COMPATIBILITY.md`——把用户可见承诺与内部迁移进度混表；③复活参数级 YAML——重复已被推翻的决策；④放 `docs/`——无法用 `[[test]]` 保证守卫运行。
- **Consequences:** 新增一个测试数据树与一个 compat 守卫；账本行数随 wave 增长，守卫必须从第一天强制必填字段。
- **Revisit when:** 场景行超过约 2000 条且 TOML 树 review 成本明显高于单文件表格时，另立 ADR。

### ADR-CT-04: 首个 wave 选 t4，候选集由可复算流水线确定并硬上限 12 个源文件

- **Status:** Accepted
- **Context:** 按 `plan-long.md` CT-01 的族级阻塞比，t4 是候选集内占比最高且不触碰 ref 存储与协议的族，但 grit 侧 t4 文件数远超 G-04 的规模上限。

  ```sh
  # grep 的退出码 1（零命中）是合法结果，>1 才是执行失败，两者必须分开判定。
  # 用法：GRIT_REPO=<grit 仓库路径> sh tests/compat-ledger/t4/SELECTION.sh
  # 输出：选中的 12 个文件名，逐行写 stdout（EXPECTED.txt 与此逐行比对）。

  # 必须用 if/else 捕获状态；1 = 零命中（合法），>1 = 执行失败。
  [ "$rc" -le 1 ] || { echo "FAIL: grep -L failed with $rc" >&2; exit "$rc"; }
  LC_ALL=C sort "$W/struct.raw" > "$W/struct"

    [ "$bad" -eq 0 ] && echo "$f" >> "$W/final"

  LC_ALL=C sort -o "$W/final" "$W/final"

  head -12 "$W/final"                                                           # ← stdout：首批 12
  # 溢出段写 stderr（与 stdout 的选中清单分开，便于 EXPECTED.txt 逐行比对）

    echo "### overflow (file-level; not [[scenario]] rows)"
    tail -n +13 "$W/final" | sed 's#$# | blocked | DEFER-02#'
  } >&2                                                                          # 溢出 112
  ```

### ADR-CT-05: 每个发布切片推送版本 tag

- **Status:** Accepted
- **Context:** ER-08 要求版本面四处一致，因此每次 patch bump 都会改写 `install.sh` 的 `DEFAULT_VERSION`（`install.sh:21`）。该值是 release API 不可达时的下载回落版本（`install.sh:17-21`、`:609-624`），而产物只由 `release.yml` 在 `push` `v*` tag 时构建上传（`release.yml:3-6`）。若只 bump 不推 tag，回落路径会指向一个在 R2 上不存在的版本。仓库现有 tag（`v0.18.91`–`v0.18.93`、`v0.19.26`、`v0.19.63`）证明 tag 机制在用，但并非每个 patch 都有。
- **Decision:** 本计划的每个发布切片在 ER-04 C 组第 ⑦ 步之后执行第 ⑧ 步：`libra tag v<version>` + `libra push origin v<version>`，并把产物可获取性作为 D-02 远端后置门。
- **Alternatives considered:** ①只 bump 不推 tag——会让 `DEFAULT_VERSION` 指向不存在的产物，是可观测的用户面退化；②不 bump 版本——违反 ER-08（implementation 卡必须递增）；③只 bump `Cargo.toml` 不改 `install.sh`——违反 ER-08 的四处 parity。
- **Consequences:** 本计划产出 4 个用户可获取的 patch release；C 组第 ⑧ 步与 D-02 对每个发布卡生效；`Rollback mode` 因此必须是 `compensating`（已发布 tag 不撤回，靠前滚新版本补偿）。
- **Revisit when:** 仓库确立「patch 版本不发布产物」的显式政策，并相应调整 `install.sh` 的回落语义。

## 任务卡

### 任务卡粒度规则（强制）

本节转录自 `docs/development/plan/plan-template.md` v2；条款以模板为准。任一条不满足即为「粒度不合格」，必须在开工前拆分或合并，并同步实施顺序、依赖登记表、发布分组、追溯表、测试矩阵、里程碑、风险表与修订历史。

- **G-01 单一行为轴与恢复模式（上限）:** 一张卡只承担一个可独立恢复的行为轴，且存在单一已声明的恢复动作。`Rollback mode` 取 `revert` / `forward-only` / `compensating` / `immutable-release` 之一。
- **G-02 完整可交付（下限）:** 同一行为轴的实现、测试、文档、兼容矩阵与索引同步属于同一张卡，禁止拆成「实现卡 / 补测试卡 / 补文档卡」。
- **G-03 条目上限与计数口径:** `implementation`/`migration`/`removal`/`spike` 的 AC 与 Verification 上限各 8；`release` 为 12；`docs`/`audit`/`handoff` 为 20。AC 按独立 pass/fail 谓词计（「且/并且/以及/同时」连接的可分别失败的断言分别计；嵌套子列表与表格行逐项计）；Verification 按独立验证门计（环境准备前缀与其后命令合计一门；一条命令中多个 `--test` target 分别计；`&&` 串联两个独立判定按两门计）。ER-04 的强制门不计入。
- **G-04 规模上限（可计数）:** `Estimated scope` 开工态只允许 `S` 或 `M`。计数只统计承载本卡行为变更的**生产**落点与文件（`src/**`、`sql/migrations/**`、`web/src/**`、`worker/src/**` 等）；本卡自己的测试文件、按 GC-05/ER-06 强制同步的文档集、测试索引与注册面、以及 ER-08 的版本面四处属「随附同步集」，**不计入**。`S` = ≤ 2 落点 / ≤ 3 生产文件且无 schema/协议/公开接口变更；`M` = ≤ 4 落点 / ≤ 12 生产文件、最多一处公开行为或接口变化。
- **G-05 Agent 可独立执行:** 每卡自带可核对的 `file:line` 锚点、自洽的 AC、可直接复制执行的 Verification 命令，`Dependencies` 只引用任务 ID 或 `DEP-*`。
- **G-06 依赖闭合且无环:** 计划内依赖直接引用任务 ID；跨计划与外部前置必须先登记 `DEP-*`。「实施顺序」的边与各卡 `Dependencies` 必须一致。
- **G-07 发布切片对齐:** 默认「一张卡 = 一个发布切片」。`docs`/`audit`/`spike`/`handoff` 卡不 bump、不产 artifact，`Release boundary` 写 `no-release` 并说明其产物随哪次发布进入用户渠道。任何多卡合并发布必须登记 `REL-*`。
- **G-08 家族卡:** 只有当变更确实无法切成可独立发布的切片时才用家族卡，且唯一发布点卡的 `Task type` 必须是 `release`。**本计划不使用家族卡**：REL-01 / REL-02 是串行窗口 + `no-release` 卡的 C 覆盖继承，承载点均为 `independent` 的普通发布卡。
- **G-09 拆分协议:** 拆分已被引用的卡时原编号保留给主轴，新子卡在所属 Phase 末尾追加编号，并同步全部交叉引用与「修订历史」。**本计划成稿后未发生卡拆分**（R1 修订为字段与判据订正，编号不变）。
- **G-10 写集与并发:** 每卡声明 `Implementation write set`（I）与 `Release write set`（R）。I–I 相交禁止并发且无豁免通道，只能补顺序边或合并到唯一集成卡；I–R 相交在串行发布窗口内由写锁处理；R–R 相交由 ER-12 的串行窗口顺序化。

#### Verification 判定口径

- **零命中守卫必须区分「无命中」与「命令失败」。** `rg` 退出码 `0` = 有命中、`1` = 零命中、`>1` = 执行失败。`! rg …` 与 `if rg …; then exit 1; fi` 都会把 `>1` 误判为通过；裸 `rg …; rc=$?` 在 `set -e` 下也不行。统一使用下列模板：

  ```bash
  if rg -n "<pattern>" <paths>; then
    echo "FAIL: forbidden pattern found"; exit 1
  else
    rc=$?
    if [ "$rc" -ne 1 ]; then echo "ERROR: rg failed with exit $rc"; exit "$rc"; fi
    echo "OK: zero hits"
  fi
  ```

- 当被检查对象是**目录或文件是否存在**时，不得用内容检索代替存在性断言，必须用 `test -d` / `test -e` 并显式判定。
- 当零命中守卫的输入来自另一条命令时，必须先捕获该命令的输出与退出码并校验其成功，再把输出交给 `rg`；不得直接管道（管道会掩盖上游失败）。
- 「只允许 allowlist 命中」类守卫必须逐条比对固定 allowlist，并在任务记录中附命中 diff。
- 仅用于定位符号的 `rg` 必须注明「锚点定位用，非判据」。
- 本任务新增的 test fn / 场景过滤必须标 `(new)`，并确保其所属 `--test` target 已存在或在同卡内注册（`tests/compat/*` 还需 `Cargo.toml` `[[test]]`）并同步 `tests/INDEX.md`。
- `cargo test --all` 不能替代任务指定用例（ER-04）；指定用例也不能替代计划完成前的全量 L1 门。

### 字段全局默认与例外

- **Release boundary 默认:** 每张卡独立发布切片；`no-release` 卡按各自登记取值。
- **Task type 默认:** `implementation`
- **Rollback mode 默认:** `compensating`（本计划所有卡的变更最终都进入已推送到 `origin/main` 的提交，且发布卡另有已推送的 tag 与 R2 产物；已推送内容一律前滚补偿，不回退）

  **补偿动作的统一幂等约定（G-01 要求的幂等键，全卡适用，卡内不重复）：**
  - **幂等键** = `revert(<TASK-ID>)@<被补偿的 forward commit 短 SHA>`，写在补偿提交 subject 里。它同时绑定任务与**具体目标提交**，因此同一张卡的第二次 forward 变更需要各自独立的补偿，不会被历史补偿误判为已完成。查重：`libra log --oneline | command grep -c "revert(<TASK-ID>)@<sha>"`，结果 ≥ 1 即跳过。
  - **前置状态判据（严格三态，逐路径判定；禁止二态简化）** = 该卡 forward 提交时必须为 `Implementation write set` 与 `Deliverables` 的**每一个具体路径**记录两组摘要并随任务记录留存：`PRE`（forward 之前的 sha256；当时不存在则记 `absent`）与 `POST`（forward 之后的 sha256；被删除则记 `absent`）。补偿前逐路径计算 `NOW` 并判定：
    - 全部 `NOW == PRE` → **已完成**，整体 no-op，不产生任何提交；
    - 全部 `NOW == POST` → **可补偿**，按依赖逆序恢复**全部**路径；
    - 其余任何组合（含部分匹配）→ **冲突**，立即停止并升级人工核对，禁止覆盖或删除。

    「仅凭 `NOW != POST` 即判为已完成」是被明确禁止的二态判据。禁止无条件 `rm`/`rm -rf <目录>` 做补偿——目录可能已含其它卡的产物（例如 `tests/compat-ledger/t4/` 同时被 CT3-01 与 CT3-02 写入）。
  - **重复执行判据** = 补偿脚本按具名路径覆盖写或删除，可重复运行；再次运行时三态判定会落到「已完成」并 no-op。`libra commit` 在无差异时失败退出，同样视为「已完成」而非错误。
  - **验证命令** = 补偿推送后 `libra rev-parse origin/main` 与本地一致，且该卡的 focused 用例回到变更前的预期结果。
  - **发布卡额外说明**：已推送的 tag 与已上传的 R2 产物**不撤回**（`immutable-release` 语义的部分），补偿靠更高的 patch 版本 + 新 tag；用户影响 = 中间版本存在一次行为变化，降级指引写在补偿提交的 CHANGELOG 条目中。
- **Migration and rollback 默认:** `N/A：本计划无 schema 迁移`

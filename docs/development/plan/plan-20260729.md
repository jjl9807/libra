# 上游 Git 兼容测试迁移第一批计划（2026-07-29）

**模板版本:** 依据 `docs/development/plan/plan-template.md` `v2`（2026-07-28 生效）整份编写。本文「任务卡粒度规则（强制）」与「Verification 判定口径」两节转录自模板 v2；如与模板正文冲突，一律以模板为准。

## 文档职责

本文解决 `plan-long.md` 的 **CT-01（上游 Git 套件驱动的兼容性证据账本 / Grit Git 兼容测试迁移）** 的第一批可执行范围，目标是交付：合规与族级范围裁定、两项由分歧探测确证的 Git 兼容缺陷修复、一套带强制字段的兼容证据账本与其守卫，以及 t4（diff / format-patch）族首批场景从上游语料到 Libra 原生测试的 clean-room 迁移。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `libra config <key>` 对**非敏感 key** 的裸读、`libra update-ref` 的 `<newvalue>`/`<oldvalue>` 操作数解析这两条 Git 兼容表面。
- 兼容证据账本的落点、schema、必填字段与 compat 守卫（`tests/compat-ledger/`、`tests/compat/compat_ledger_schema.rs`）。
- t4 族首批（≤ 12 个上游文件所含场景）的清单、四分类，以及其中 `direct` 场景重写为 Libra 原生 Rust 集成测试。
- Grit 相关的族级范围裁定文档、`D` 编号绑定，以及既有 Grit 文档债收口。
- 四个发布切片的版本递增、tag 推送与发布证据（ADR-CT-05）。

### 非目标

- **不 vendor 上游 GPLv2 语料**：不把 `t*.sh`、`test-lib*.sh`、`t/helper`、C helper 或其逐字预期输出复制/翻译进本仓库（ADR-CT-01）。
- **不建离线 gap 发现器**（其持久化模型按 `plan-long.md` CT-01：代码入库、上游语料不入库）：S2 阶段整体延后（DEFER-01），因其同时受 DEP-01 许可裁定与 DEP-02（SB-04 测试隔离基线）阻塞。`pass`/`fail`/`skip`/`xfail`/`timeout` 五分列统计口径随 S2 一并延后——clean-room 重写路径不产生这五种结果，只产生分类。
- **不做 t4 之外的族 wave**，也不在本计划内处理 t4 的 `adapted` 场景：移交后续日期计划（DEP-03、DEFER-02）。
- **不改 commit/tag 对象编码**（DEFER-03）、**不改 index 编码**（DEFER-04）、**不改外部 crate `git-internal`**（DEFER-05）。
- **不改 `.libra` 仓库模型**：不新增 `--git-dir`/`--work-tree`/`-C`，不做 `git → libra` 的 argv[0] 分派。
- **不引用 Grit 通过率作为目标或完成判据**（`plan-long.md`「不采纳未经限定的竞品指标」）。

### 成功定义

- 对**非敏感** key，`libra config <key>` 与 `git config <key>` 在已设置 key 上行为一致（stdout 为最后一个值、退出码 0），未设置时 exit 1 + `LBR-CLI-002`。**敏感 key 不在对齐范围内**：它们保留 Libra-only 的交互式安全赋值入口，作为已裁定的有意差异登记在 `COMPATIBILITY.md`（见 CT1-01 的 `Out of scope`）。
- `libra update-ref refs/heads/<name> <rev>` 接受**本身即 commit** 的 revision 表达式，`<ref>` 操作数的既有 `refs/heads/*` 收窄不变。
- 仓库内存在场景级兼容证据账本，其每条场景都带 `reason` / `category` / `owner` / `review_date`，并由已注册的 compat 守卫强制。
- t4 首批 `direct` 场景已作为 Libra 原生测试运行通过，且候选集可由已提交的命令流水线复算出同一结果。
- 全部非延后任务 `Lifecycle=done` 且 `Acceptance=complete`，Codex review 结论为 `PASS`。

## 事实基线

> **二进制前置（开工第一步，动态预检——不得写死版本号）**：本仓库的 `.libra/libra.db` schema 会随并发节点推进（当前最新迁移为 `sql/migrations/2026072502_workspace_paging_index.sql`）。若**已安装**的 `libra` 早于该 schema，它在本仓库内的任何命令（含 ER-01 的 `libra status --short --branch`）都会以 `LBR-IO-001` / 退出码 128 失败。因此开工第一步是**先探测、按需构建**，而**不是**无条件覆盖安装：
>
> ```sh
> set -eu
> libra --version                      # 记录已安装版本
> if libra status --short --branch >/dev/null 2>&1; then
>   echo "OK: installed libra is schema-compatible with this repo; use it as-is"
> else
>   echo "installed libra cannot open this repo; building from source"
>   LIBRA_SKIP_WEB_BUILD=1 cargo build --release
>   ./target/release/libra status --short --branch >/dev/null \
>     || { echo "FAIL: freshly built binary still cannot open the repo; fix migrations first"; exit 1; }
>   echo "OK: use ./target/release/libra for the rest of this plan"
> fi
> ```
>
> **禁止用源码构建覆盖一个版本更高的已安装二进制**：2026-07-30 实测已安装 `libra 0.19.82` > 源码 `Cargo.toml` 的 `0.19.81`，且 `libra status --short --branch` 退出码为 0，因此本次**无需**构建安装，直接使用已安装的 `libra`。只有当上面的探测判定不兼容、且构建产物确实能打开本仓库时，才把它安装到 `$HOME/.libra/bin/libra`（macOS 另需 `codesign --force --sign - $HOME/.libra/bin/libra`），或直接以 `./target/release/libra` 路径使用而不安装。本节所有「实测」证据都必须记录所用二进制的路径与 `--version`。仅在**隔离的新建仓库**中（不受本仓库 schema 影响）取得的证据可沿用，但须注明。
>
> 所有行号和源码锚点必须在开工当天刷新。过期锚点只能作为历史线索。**核对日期：2026-07-30，`main` @ `c716b73a5d6163ec65b73ac6c8987912aeac293c`，`Cargo.toml` 版本 `0.19.81`**（上一次核对为 2026-07-29 @ `88b5cf4c3d1e236c32a0a3a7c3ef7120adeaf76f`，其快照见「PRE 快照」小节）。所有计数类事实附可复算命令；复算时必须用 `command grep` 或把命令写入脚本后 `sh script.sh` 执行，避免交互 shell 层的 `grep` 别名/函数包装改变结果。
>

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-CT-01: 迁移形态为 clean-room 场景重写，不 vendor 上游语料

- **Status:** Accepted
- **Context:** grit 的 `grit-git`、`/git`、`/tests` 是 GPLv2，Libra 是 MIT（`grit/LICENSE`、`Cargo.toml:5`）。`docs/development/gap/grit-gap.md:413` 已把「不得复制或翻译 GPLv2 来源的源码、shell harness、C helper、`t*.sh` 文本或其逐字预期输出」写成高风险质量门；`:93` 另行禁止把 grit 的 shell harness 作为 Libra 的测试接入形态。
- **Decision:** 「迁移」= 迁移**测试覆盖面**。归纳上游测试的场景、前置状态、操作步骤、断言与边界，用 `tests/command/*`、`tests/helpers/`、`tests/harness/` 的既有 Libra 写法重写；断言写 Libra 的实测预期。允许保留的只有短小数据型 fixture，且必须记录来源 tag/commit、许可证与不能由 Libra helper 生成的理由。
- **Alternatives considered:** ①整体 vendor `t*.sh` + 移植 harness——被许可证与既有决策否决；②仓库外运行上游语料作 gap 发现器——「仅运行而不分发」是否合规无裁定（DEP-01），且探针违反尚未落地的 SB-04 隔离要求（DEP-02），整体延后为 DEFER-01。
- **Consequences:** 迁移吞吐较低但可 review、可维护、无许可风险；覆盖面完整性依赖清单卡，因此账本（CT2-01）是必需品。
- **Revisit when:** DEP-01 给出明确裁定且 SB-04 已落地。

### ADR-CT-02: 初始分支名走既有 `init.defaultBranch`，不新增 `GIT_TEST_*` 环境变量读取

- **Status:** Accepted
- **Context:** 上游套件用 `GIT_TEST_DEFAULT_INITIAL_BRANCH_NAME` 统一初始分支名。现状核对显示 Libra 已支持 `init.defaultBranch` 级联与 `-b/--initial-branch`（`src/command/init.rs:250-263`（`-b` 短选项声明）与 `:496-521`（级联解析）、`COMPATIBILITY.md:103`）。
- **Decision:** 不在生产代码中读取任何 `GIT_TEST_*` 变量。迁移后的测试通过 `libra init -b <name>` 或预置 `init.defaultBranch` 达成同一效果。
- **Alternatives considered:** 读取该变量——会把上游测试专用变量固化进生产语义，并与 `init.defaultBranch` 形成第二个事实源，违反 GC-02。
- **Consequences:** `plan-long.md` CT-01 的 S1 候选项列表需订正（CT0-01 承接）。
- **Revisit when:** 出现必须在生产路径识别上游测试环境的需求（当前无）。

### ADR-CT-03: 兼容证据账本的落点、粒度与格式

- **Status:** Accepted
- **Context:** `docs/development/commands/_compatibility.md:93` 记录了一次已执行的反向决策——删除参数级 YAML 及其 `test_evidence` / `last_verified` 字段。`plan-long.md` 要求排除项必带 `reason`/`category`/`owner`/`review date`，且账本以**场景**为行。`tests/compat/matrix_alignment.rs:295-298` 禁止新建顶层 `scripts/`。
- **Decision:** 账本落在 `tests/compat-ledger/<family>/<stem>.toml`，**一个上游源文件一个 TOML，文件内以 `[[scenario]]` 数组承载多条场景行**；场景 ID 为 `<stem>::<upstream_test_name_slug>`，稳定且与上游测试标题一一对应。每条 `[[scenario]]` 必填 `id`、`category`（闭集 `direct`/`adapted`/`declined`/`blocked`）、`reason`、`owner`、`review_date`（ISO 8601 日期）、`upstream_revision`（40 位 hex 的 pinned grit SHA）、`upstream_file`（源脚本文件名）、`libra_command`（对应 Libra 命令）、`libra_surface`（对应 flag / 子面）；`declined` 另必填 `decision_id`（`D<n>` 或具名 `D-*`），`blocked` 另必填 `blocked_by`。`libra_tests` **不是 schema 级必填字段**（分类阶段尚无测试函数名），其完备性由 CT3-02 的收口守卫单独强制：wave 收口时每条仍为 `direct` 的场景都必须有非空 `libra_tests`。账本**不**复制 `COMPATIBILITY.md` 的 tier，也不承载参数级 `test_evidence`。运行结果统计（`pass`/`fail`/`skip`/`xfail`/`timeout`）不属于本 schema——clean-room 重写只产生分类，统计随 DEFER-01 的离线发现器一并定义。
- **Alternatives considered:** ①一个源文件一行——与 `plan-long.md` 的场景级要求冲突，且同一脚本内常有混合分类；②写进 `COMPATIBILITY.md`——把用户可见承诺与内部迁移进度混表；③复活参数级 YAML——重复已被推翻的决策；④放 `docs/`——无法用 `[[test]]` 保证守卫运行。
- **Consequences:** 新增一个测试数据树与一个 compat 守卫；账本行数随 wave 增长，守卫必须从第一天强制必填字段。
- **Revisit when:** 场景行超过约 2000 条且 TOML 树 review 成本明显高于单文件表格时，另立 ADR。

### ADR-CT-04: 首个 wave 选 t4，候选集由可复算流水线确定并硬上限 12 个源文件

- **Status:** Accepted
- **Context:** 按 `plan-long.md` CT-01 的族级阻塞比，t4 是候选集内占比最高且不触碰 ref 存储与协议的族，但 grit 侧 t4 文件数远超 G-04 的规模上限。
- **Decision:** 候选集由下列**已在本计划内展开、并已于 2026-07-29 实跑过一次**的流水线产生（CT3-01 只负责重跑、比对并落账，不再自行设计规则）。工作目录固定为 grit 仓库的 `tests/`，grit revision pin 为 `dfb079967b9c`：

  ```sh

  # tests/compat-ledger/t4/SELECTION.sh — 复算 t4 首批候选。
  # 约定：所有管道都拆成「生产者写临时文件 + 显式检查退出码 + 消费者单独运行」。
  # POSIX sh 没有 pipefail，`producer | sort > f` 的退出码取自 sort，会吞掉生产者失败。
  # grep 的退出码 1（零命中）是合法结果，>1 才是执行失败，两者必须分开判定。
  # 用法：GRIT_REPO=<grit 仓库路径> sh tests/compat-ledger/t4/SELECTION.sh
  # 输出：选中的 12 个文件名，逐行写 stdout（EXPECTED.txt 与此逐行比对）。
  set -eu
  PIN=dfb079967b9cbc99e533c21e65f674bb3f5e8b07
  : "${GRIT_REPO:?set GRIT_REPO to the grit checkout}"
  # LIBRA_ROOT 优先取显式环境变量；否则从脚本位置推导，并强制校验命中的确是 Libra 仓库根。
  LIBRA_ROOT=${LIBRA_ROOT:-$(CDPATH= cd -- "$(dirname -- "$0")/../../.." && pwd)}
  [ -f "$LIBRA_ROOT/COMPATIBILITY.md" ] && [ -d "$LIBRA_ROOT/.libra" ] \
    || { echo "FAIL: LIBRA_ROOT=$LIBRA_ROOT is not a Libra repo root; set LIBRA_ROOT explicitly" >&2; exit 1; }
  head=$(git -C "$GRIT_REPO" rev-parse HEAD)
  [ "$head" = "$PIN" ] || { echo "FAIL: grit HEAD $head != pinned $PIN" >&2; exit 1; }
  # 仅 pin HEAD 不够：tests/ 下的已跟踪修改或未跟踪文件会改变枚举结果而不改变 SHA。
  # 必须显式捕获 git 的退出码——`[ -z "$(git ...)" ]` 在 git 失败时同样得到空串而误判为干净。
  st=$(git -C "$GRIT_REPO" status --porcelain -- tests) \
    || { echo "FAIL: git status failed in $GRIT_REPO" >&2; exit 1; }
  [ -z "$st" ] || { echo "FAIL: grit tests/ is dirty; clean it before recomputing" >&2; exit 1; }
  W=$(mktemp -d); trap 'rm -rf "$W"' EXIT INT TERM

  # 步骤 0：全集（t4 四位编号）
  cd "$GRIT_REPO/tests"
  command ls t4[0-9][0-9][0-9]-*.sh > "$W/all.raw" || { echo "FAIL: ls t4*.sh" >&2; exit 1; }
  LC_ALL=C sort "$W/all.raw" > "$W/all"
  [ "$(wc -l < "$W/all")" -eq 180 ] || { echo "FAIL: stage0 count != 180" >&2; exit 1; }

  # 步骤 1：结构筛选（排除仓库布局 / 上游 helper / 外部服务 / submodule / update-ref）
  if command grep -LE '\.git/|\$GIT_DIR/|--git-path|(^|[^-[:alnum:]_])test-tool([[:space:]]|$)|lib-httpd\.sh|lib-git-daemon\.sh|lib-git-p4\.sh|lib-git-svn\.sh|lib-cvs\.sh|lib-gitweb\.sh|lib-gpg\.sh|(^|[^-[:alnum:]_])git[[:space:]]+submodule([[:space:]]|$)|(^|[^-[:alnum:]_])git[[:space:]]+update-ref([[:space:]]|$)' \
      $(cat "$W/all") > "$W/struct.raw"; then rc=0; else rc=$?; fi
  # 注意：`cmd > f; rc=$?` 在 `set -e` 下会因 grep 的合法退出码 1 直接终止脚本，
  # 必须用 if/else 捕获状态；1 = 零命中（合法），>1 = 执行失败。
  [ "$rc" -le 1 ] || { echo "FAIL: grep -L failed with $rc" >&2; exit "$rc"; }
  LC_ALL=C sort "$W/struct.raw" > "$W/struct"
  [ "$(wc -l < "$W/struct")" -eq 145 ] || { echo "FAIL: stage1 count != 145" >&2; exit 1; }

  # 步骤 2：命令面筛选。命令清单 = COMPATIBILITY.md「Top-level commands」主表的 108 个数据行
  # （该表本身**不含** unsupported 行；`submodule`/`sparse-checkout`/`send-email` 位于独立的
  #  「intentionally absent」表 :260-262，因此天然不在清单内，无需另做减法）。
  awk 'NR>=103 && NR<=210 {split($0,f,"|"); gsub(/^[ \t]+|[ \t]+$/,"",f[2]); if (f[2]!="") print f[2]}' \
      "$LIBRA_ROOT/COMPATIBILITY.md" > "$W/cmds.raw" || { echo "FAIL: awk COMPATIBILITY.md" >&2; exit 1; }
  LC_ALL=C sort -u "$W/cmds.raw" > "$W/cmds"
  [ "$(wc -l < "$W/cmds")" -eq 108 ] || { echo "FAIL: command inventory != 108" >&2; exit 1; }
  : > "$W/final"
  while read -r f; do
    bad=0
    if command grep -hoE '(^|[^-[:alnum:]_./"])git( +-[^ ]+)* +[a-z][a-z0-9-]*' "$f" > "$W/subs.raw"; then rc=0; else rc=$?; fi
    [ "$rc" -le 1 ] || { echo "FAIL: grep subcommands in $f failed with $rc" >&2; exit "$rc"; }
    awk '{print $NF}' "$W/subs.raw" > "$W/subs.f" || { echo "FAIL: awk subs" >&2; exit 1; }
    LC_ALL=C sort -u "$W/subs.f" > "$W/subs"
    for sub in $(cat "$W/subs"); do
      command grep -qx "$sub" "$W/cmds" || { bad=1; break; }
    done
    [ "$bad" -eq 0 ] && echo "$f" >> "$W/final"
  done < "$W/struct"
  LC_ALL=C sort -o "$W/final" "$W/final"
  [ "$(wc -l < "$W/final")" -eq 124 ] || { echo "FAIL: stage2 count != 124" >&2; exit 1; }

  # 步骤 3：确定性截断。选中清单写 stdout（EXPECTED.txt 与之比对）；
  # 溢出清单写 stderr（与 stdout 的选中清单分开），不落独立文件。
  # 注意：这里同样不得用 `tail … | sed`——POSIX sh 下管道退出码取自 sed，会吞掉 tail 的失败。
  head -12 "$W/final" > "$W/sel" || { echo "FAIL: head -12" >&2; exit 1; }
  [ "$(wc -l < "$W/sel")" -eq 12 ] || { echo "FAIL: selected != 12" >&2; exit 1; }
  cat "$W/sel"                                                                   # ← stdout：首批 12
  tail -n +13 "$W/final" > "$W/ovf.raw" || { echo "FAIL: tail -n +13" >&2; exit 1; }
  sed 's#$# | blocked | DEFER-02#' "$W/ovf.raw" > "$W/ovf" \
    || { echo "FAIL: sed overflow" >&2; exit 1; }
  [ "$(wc -l < "$W/ovf")" -eq 112 ] || { echo "FAIL: overflow != 112" >&2; exit 1; }
  # 溢出段写 stderr（与 stdout 的选中清单分开，便于 EXPECTED.txt 逐行比对）
  echo "### overflow (file-level; not [[scenario]] rows)" >&2
  cat "$W/ovf" >&2                                                               # 溢出 112
  ```

### ADR-CT-05: 每个发布切片推送版本 tag

- **Status:** Accepted
- **Context:** ER-08 要求版本面四处一致，因此每次 patch bump 都会改写 `install.sh` 的 `DEFAULT_VERSION`（`install.sh:21`）。该值是 release API 不可达时的下载回落版本（`install.sh:17-21`、`:609-624`），而产物只由 `release.yml` 在 `push` `v*` tag 时构建上传（`release.yml:3-6`）。若只 bump 不推 tag，回落路径会指向一个在 R2 上不存在的版本。仓库现有 tag（`v0.18.91`–`v0.18.93`、`v0.19.26`、`v0.19.63`）证明 tag 机制在用，但并非每个 patch 都有。
- **Decision:** 本计划的每个发布切片在 ER-04 C 组第 ⑦ 步之后执行第 ⑧ 步：`libra tag v<version>` + `libra push origin v<version>`，并把产物可获取性作为 D-02 远端后置门。
- **Alternatives considered:** ①只 bump 不推 tag——会让 `DEFAULT_VERSION` 指向不存在的产物，是可观测的用户面退化；②不 bump 版本——违反 ER-08（implementation 卡必须递增）；③只 bump `Cargo.toml` 不改 `install.sh`——违反 ER-08 的四处 parity。
- **Consequences:** 本计划产出 4 个用户可获取的 patch release；C 组第 ⑧ 步与 D-02 对每个发布卡生效；`Rollback mode` 因此必须是 `compensating`（已发布 tag 不撤回，靠前滚新版本补偿）。
- **Revisit when:** 仓库确立「patch 版本不发布产物」的显式政策，并相应调整 `install.sh` 的回落语义。

## 执行检查必备需求（强制）

`ER-01` 至 `ER-12` 按模板全量适用，本文不复述。本计划的具体化取值：

- **`LIBRA_SKIP_WEB_BUILD=1`（规范条款，所有 Rust 门必带）**：`build.rs` 默认会驱动 Next.js/Turbopack 构建 `web/`。在干净的 `CARGO_TARGET_DIR` 下，这会让**与 web 无关**的 Rust 门依赖 Node 与端口权限——2026-07-30 实测在受限环境中 `build.rs` 因 Turbopack `binding to a port: Operation not permitted` 以 101 退出，导致 CT1-01 的 focused 门无法执行；加上 `LIBRA_SKIP_WEB_BUILD=1` 后同一组用例通过。因此本计划**每一条** `cargo` 门（含 `-- --list` 前置门）都必须带该变量：复合门在脚本开头 `export LIBRA_SKIP_WEB_BUILD=1`，单行门写成 `source .env.test && LIBRA_SKIP_WEB_BUILD=1 cargo test …`。唯一例外是 ER-04 C 组的 `pnpm --dir web …` / `pnpm --dir worker …` 六个门——它们**就是**要构建 web/worker，不得设置该变量。

- **focused 用例的「零命中即失败」规则（规范条款；各卡 `Verification` 内**逐条内联展开**，本节不留占位符）**：Cargo 的子串过滤在零匹配时仍以 0 退出（实测 `cargo test --test command_test <不存在的过滤> -- --list` 输出 `0 tests` 且退出码 0）。因此本计划中**每一条** `cargo test --test <target> [<filter>]` 门都必须写成复合门：先 `-- --list` 断言该卡承诺的**每一个**具名测试函数都出现、且 `: test` 行数不少于承诺数量，再真正执行。无过滤的整目标门（如 `compat_ledger_schema`）同样适用——必须逐个列出该卡承诺的 fn 名。各卡的完整命令见其 `Verification`。

- **ER-04 的 A 组（表面 focused 门）**：各卡在其 `Verification` 中给出**已展开的**确切命令，本节不留占位符。`src/**` 改动的两张卡分别是 `source .env.test && LIBRA_SKIP_WEB_BUILD=1 cargo test --test command_test config_bare_read`（CT1-01）与 `source .env.test && LIBRA_SKIP_WEB_BUILD=1 cargo test --test command_test update_ref_revision`（CT1-02）；`Cargo.toml` 非版本行改动（CT2-01 的 `[[test]]` 注册）→ `source .env.test && LIBRA_SKIP_WEB_BUILD=1 cargo test --test compat_ledger_schema`；只改文档的卡无表面门，只走 B 组结构与链接门。
- **`install.sh` 表面门（每张发布卡必跑）**：因 ER-08 的四处 parity 会改写 `install.sh` 的 `DEFAULT_VERSION`，每张发布卡的 A 组另加两条：

  ① 语法门 `bash -n install.sh`。

  ② **关键路径冒烟**（走到平台探测、URL 构造、下载与安装写入，而不是只打印 help）：用 `install.sh` 已支持的 `LIBRA_BASE_URL` / `LIBRA_VERSION` 覆盖点（`install.sh:14,222-237,610`）指向本地 fixture。

  ⚠️ **必须屏蔽公网**：`install.sh:470` 的 `probe_network` 会**无条件**用 `curl`/`wget` 访问 `https://libra.tools`（调用点 `install.sh:558`），且当前没有跳过开关。它失败只是打印一条 warn 而不中断安装，但会让这个「本地 fixture 冒烟」实际产生网络出口。因此冒烟必须在 `PATH` 最前面放一个受控 downloader wrapper，只放行 fixture URL、拒绝一切 `http(s)://`：

  ```sh
  set -eu
  root=$(mktemp -d); ver=v0.0.0-smoke
  os=$(uname -s | tr 'A-Z' 'a-z'); case $(uname -m) in arm64|aarch64) arch=arm64;; *) arch=amd64;; esac
  mkdir -p "$root/serve/$ver" "$root/shim" "$root/home"   # 预建 home，避免 install.sh:756 写 .profile 时的无害噪声
  cp "$(command -v libra)" "$root/serve/$ver/libra-$os-$arch"

  # downloader wrapper：拒绝任何 http(s) URL（含 probe_network 的 https://libra.tools），
  # 其余参数透传给真实二进制。这样冒烟严格离线，且 probe 失败只会走 warn 分支。
  real_curl=$(command -v curl || true); real_wget=$(command -v wget || true)
  for tool in curl wget; do
    real=$(eval "printf '%s' \"\$real_$tool\"")
    [ -n "$real" ] || continue
    cat > "$root/shim/$tool" <<SHIM
  #!/bin/sh
  for a in "\$@"; do
    case "\$a" in http://*|https://*)
      echo "smoke: blocked network URL \$a" >&2; exit 1 ;;
    esac
  done
  exec "$real" "\$@"
  SHIM
    chmod +x "$root/shim/$tool"
  done

  env PATH="$root/shim:$PATH" HOME="$root/home" LIBRA_HOME="$root/lh" \
      LIBRA_BASE_URL="file://$root/serve" LIBRA_VERSION="$ver" \
      sh install.sh -d "$root/bin" --no-alias
  test -x "$root/bin/libra" || { echo "FAIL: installer did not write the binary"; exit 1; }
  "$root/bin/libra" --version >/dev/null || { echo "FAIL: installed binary not runnable"; exit 1; }
  rm -rf "$root"; echo OK
  ```

  预期观察：安装过程会打印 `libra.tools unreachable — using fallback …` 的 warn（probe 被 shim 拒绝），随后继续用 fixture URL 完成下载与安装写入——这正是「离线可执行」的判据。若 `download_file` 的实现不支持 `file://`，则改用 `python3 -m http.server` 在 `127.0.0.1` 的临时端口上提供同一目录，并把 shim 的放行规则同步改为「只放行 `http://127.0.0.1:<port>/`，其余 http(s) 一律拒绝」；两种形式都必须真实走完下载与安装写入，且都不得产生对外网络出口。
- **ER-04 的 C 组**：版本 bump 会改写 `web/package.json` 与 `worker/package.json`，因此每个发布切片的 C 组在三门之外**另加** `pnpm --dir web lint`、`pnpm --dir web test`、`pnpm --dir web build`、`pnpm --dir worker lint`、`pnpm --dir worker test`、`pnpm --dir worker build`（脚本名以各自 `package.json` 的 `scripts` 为准，2026-07-29 核对存在）。本计划不触及 Cloudflare 运行时绑定，故不加 `test:miniflare`。
- **ER-04 的 C 组第 ⑧ 步**：按 ADR-CT-05 **执行**（非 `N/A`）：`libra tag v<version>` + `libra push origin v<version>`，并确认 tag 推送成功。
- **ER-04 的 D 组**：D-01（CodeQL）与 D-02（release 产物），见「发布分组与并发窗口」。
- **ER-08 版本面**：开工日核对为四处（`Cargo.toml:3`、`web/package.json:3`、`worker/package.json:3`、`install.sh:21`），当前一致于 `0.19.81`，parity 预检通过；每张发布卡 `Version increment = patch`，实际数字在进入发布窗口时重读 `Cargo.toml` 决定。

**D-01 执行脚本**（`GH_REPO` 必须显式给出——本仓库无 `.git`，`gh` 无法推断。**分两步执行，`libra push origin main` 是二者之间的显式边界**：先跑 ①「基线」并落盘，由发布者执行 C 组第 ⑦ 步的推送，再跑 ②「验证」。禁止在 push 之后才取基线）：

```sh
# ===== ① 基线：必须在 libra push origin main 之前运行 =====
set -eu
: "${GH_REPO:?export GH_REPO=<owner>/<repo>}"; export GH_REPO
# 分两步：先显式检查 gh 的退出码，再排序。禁止 `gh ... | sort > f`——
# POSIX `set -e` 下管道退出码取自 sort，gh 失败会被吞掉并产出空文件冒充「零 alert」。
gh api -X GET "repos/$GH_REPO/code-scanning/alerts" -f state=open -f per_page=100 --paginate \
  --jq '.[] | [.rule.id, .most_recent_instance.location.path, (.most_recent_instance.location.start_line|tostring)] | @tsv' \
  > /tmp/codeql-before.raw || { echo "FAIL: gh api (baseline) failed"; exit 1; }
LC_ALL=C sort /tmp/codeql-before.raw > /tmp/codeql-before.tsv
libra rev-parse HEAD > /tmp/codeql-expected-sha.txt
echo "OK: baseline saved ($(wc -l < /tmp/codeql-before.tsv) alerts) for $(cat /tmp/codeql-expected-sha.txt)"
echo "Now run: libra push origin main"
```

```sh
# ===== ② 验证：在 libra push origin main 之后运行 =====
set -eu
: "${GH_REPO:?export GH_REPO=<owner>/<repo>}"; export GH_REPO
test -f /tmp/codeql-before.tsv || { echo "FAIL: baseline missing; rerun step 1 BEFORE pushing"; exit 1; }
# 注意：零 alert 的仓库其基线文件为空，属合法情形；因此只判存在性，不判非空。
# API 失败在步骤 ① 由 gh 的非零退出码 + set -eu 直接中断，不会产生空基线冒充成功。
SHA=$(libra rev-parse HEAD)
[ "$SHA" = "$(cat /tmp/codeql-expected-sha.txt)" ] \
  || { echo "FAIL: HEAD moved since baseline; redo step 1"; exit 1; }
deadline=$(( $(date +%s) + 1800 ))          # 30 min，与 ER-10 的总时间预算一致
while :; do
  gh api "repos/$GH_REPO/commits/$SHA/check-runs" --paginate \
    --jq '.check_runs[] | select(.name|startswith("security-codeql-")) | [.name,.status,.conclusion] | @tsv' \
    > /tmp/codeql-checks.raw || { echo "FAIL: gh api (check-runs) failed"; exit 1; }
  LC_ALL=C sort /tmp/codeql-checks.raw > /tmp/codeql-checks.tsv
  [ "$(awk -F'\t' '$2=="completed"' /tmp/codeql-checks.tsv | wc -l)" -eq 2 ] && break
  [ "$(date +%s)" -lt "$deadline" ] || { echo "FAIL: CodeQL checks not completed in 30m"; exit 1; }
  sleep 30
done
expected='security-codeql-actions
security-codeql-rust'
got=$(awk -F'\t' '{print $1}' /tmp/codeql-checks.tsv)
[ "$got" = "$expected" ] || { echo "FAIL: unexpected check set:"; printf '%s\n' "$got"; exit 1; }
awk -F'\t' '$3!="success"{print "FAIL: "$1" -> "$3; bad=1} END{exit bad?1:0}' /tmp/codeql-checks.tsv
gh api -X GET "repos/$GH_REPO/code-scanning/alerts" -f state=open -f per_page=100 --paginate \
  --jq '.[] | [.rule.id, .most_recent_instance.location.path, (.most_recent_instance.location.start_line|tostring)] | @tsv' \
  > /tmp/codeql-after.raw || { echo "FAIL: gh api (after) failed"; exit 1; }
LC_ALL=C sort /tmp/codeql-after.raw > /tmp/codeql-after.tsv
new=$(comm -13 /tmp/codeql-before.tsv /tmp/codeql-after.tsv)
[ -z "$new" ] || { echo "FAIL: new CodeQL alerts:"; printf '%s\n' "$new"; exit 1; }
echo "OK: D-01 green for $SHA"
```

**D-02 执行脚本**（在 C 组第 ⑧ 步 `libra push origin v<version>` 之后运行）：

```sh
set -eu
: "${GH_REPO:?export GH_REPO=<owner>/<repo>}"; export GH_REPO
VER=$(awk -F'"' '/^version =/{print $2; exit}' Cargo.toml); TAG="v$VER"
BASE=https://download.libra.tools/libra/releases
TAG_SHA=$(gh api "repos/$GH_REPO/git/ref/tags/$TAG" --jq '.object.sha')

# ① 选中同时匹配 tag 与 headSha 的 run，并轮询到终态（上限 60 分钟）
deadline=$(( $(date +%s) + 3600 ))
while :; do
  gh run list --workflow release.yml --limit 50 --json databaseId,headBranch,headSha,status \
    --jq "[.[] | select(.headBranch==\"$TAG\" and .headSha==\"$TAG_SHA\")][0] | [.databaseId, .status] | @tsv" \
    > /tmp/rel-run.tsv
  RUN=$(cut -f1 /tmp/rel-run.tsv); ST=$(cut -f2 /tmp/rel-run.tsv)
  [ -n "$RUN" ] && [ "$RUN" != "null" ] && [ "$ST" = "completed" ] && break
  [ "$(date +%s)" -lt "$deadline" ] || { echo "FAIL: release run for $TAG not completed in 60m"; exit 1; }
  sleep 60
done

# ② 每一个 job 实例（含 build-and-upload 的 matrix 展开）都必须 success，且三个 job 名均出现
gh run view "$RUN" --json jobs --jq '.jobs[] | [.name,.conclusion] | @tsv' > /tmp/rel-jobs.tsv
awk -F'\t' '$2!="success"{print "FAIL: job "$1" -> "$2; bad=1} END{exit bad?1:0}' /tmp/rel-jobs.tsv
for j in build-and-upload update-homebrew-tap verify-homebrew-formula; do
  command grep -q "$j" /tmp/rel-jobs.tsv || { echo "FAIL: job $j absent from run $RUN"; exit 1; }
done

# ③ install.sh 声明支持的三个产物：HTTP 2xx 且 Content-Length > 0。
#    DEP-04 已按选项 ② 关闭——install.sh 显式拒绝 darwin/amd64，故 Intel macOS 不在集合内。
for a in libra-darwin-arm64 libra-linux-amd64 libra-linux-arm64; do
  h=$(curl -sSI "$BASE/$TAG/$a") || { echo "FAIL: curl $a"; exit 1; }
  printf '%s' "$h" | head -1 | command grep -qE ' 2[0-9][0-9] ' || { echo "FAIL: $a not 2xx"; exit 1; }
  len=$(printf '%s' "$h" | awk 'tolower($1)=="content-length:"{print $2+0}' | tail -1)
  [ "${len:-0}" -gt 0 ] || { echo "FAIL: $a empty"; exit 1; }
done

# ④ Windows 产物只断言存在，不纳入 installer 可达性（install.sh 不支持 Windows）
wh=$(curl -sSI "$BASE/$TAG/libra-windows-amd64.exe") \
  || { echo "FAIL: curl libra-windows-amd64.exe"; exit 1; }
printf '%s' "$wh" | head -1 | command grep -qE ' 2[0-9][0-9] ' \
  || { echo "FAIL: windows artifact missing"; exit 1; }

# ⑤ 两个 Homebrew job 都会 warn 后 exit 0（update 侧 release.yml:213-301，verify 侧 :330-348），
#    故 job success 不充分：逐条断言三个互不相同的本版本 URL，并断言 formula version
gh api repos/libra-tools/homebrew-libra/contents/Formula/libra.rb --jq '.content' \
  > /tmp/libra-formula.b64 || { echo "FAIL: gh api (formula) failed"; exit 1; }
base64 -d < /tmp/libra-formula.b64 > /tmp/libra-formula.rb \
  || { echo "FAIL: base64 decode of formula failed"; exit 1; }
for a in libra-darwin-arm64 libra-linux-amd64 libra-linux-arm64; do
  command grep -qF "$BASE/$TAG/$a" /tmp/libra-formula.rb \
    || { echo "FAIL: formula missing URL for $a @ $TAG"; exit 1; }
done
# 精确比较，不用把 $VER 插进 ERE（点号会成为通配，实测可让 0x19y81 冒充 0.19.81）
actual=$(sed -n 's/^[[:space:]]*version[[:space:]]*"\([^"]*\)".*/\1/p' /tmp/libra-formula.rb | head -1)
[ "$actual" = "$VER" ] || { echo "FAIL: formula version '$actual' != '$VER'"; exit 1; }
echo "OK: D-02 green for $TAG"
```

## 任务卡

### 任务卡粒度规则（强制）

本节转录自 `docs/development/plan/plan-template.md` v2；条款以模板为准。任一条不满足即为「粒度不合格」，必须在开工前拆分或合并，并同步实施顺序、依赖登记表、发布分组、追溯表、测试矩阵、里程碑、风险表与修订历史。

- **G-01 单一行为轴与恢复模式（上限）:** 一张卡只承担一个可独立恢复的行为轴，且存在单一已声明的恢复动作。`Rollback mode` 取 `revert` / `forward-only` / `compensating` / `immutable-release` 之一。
- **G-02 完整可交付（下限）:** 同一行为轴的实现、测试、文档、兼容矩阵与索引同步属于同一张卡，禁止拆成「实现卡 / 补测试卡 / 补文档卡」。
- **G-03 条目上限与计数口径:** `implementation`/`migration`/`removal`/`spike` 的 AC 与 Verification 上限各 8；`release` 为 12；`docs`/`audit`/`handoff` 为 20。AC 按独立 pass/fail 谓词计（「且/并且/以及/同时」连接的可分别失败的断言分别计；嵌套子列表与表格行逐项计）；Verification 按独立验证门计（环境准备前缀与其后命令合计一门；一条命令中多个 `--test` target 分别计；`&&` 串联两个独立判定按两门计）。ER-04 的强制门不计入。
- **G-04 规模上限（可计数）:** `Estimated scope` 开工态只允许 `S` 或 `M`。计数只统计承载本卡行为变更的**生产**落点与文件（`src/**`、`sql/migrations/**`、`web/src/**`、`worker/src/**` 等）；本卡自己的测试文件、按 GC-05/ER-06 强制同步的文档集、测试索引与注册面、以及 ER-08 的版本面四处属「随附同步集」，**不计入**。`S` = ≤ 2 落点 / ≤ 3 生产文件且无 schema/协议/公开接口变更；`M` = ≤ 4 落点 / ≤ 12 生产文件、最多一处公开行为或接口变化。
- **G-05 Agent 可独立执行:** 每卡自带可核对的 `file:line` 锚点、自洽的 AC、可直接复制执行的 Verification 命令，`Dependencies` 只引用任务 ID 或 `DEP-*`。
- **G-06 依赖闭合且无环:** 计划内依赖直接引用任务 ID；跨计划与外部前置必须先登记 `DEP-*`。「实施顺序」的边与各卡 `Dependencies` 必须一致。
- **G-07 发布切片对齐:** 默认「一张卡 = 一个发布切片」。`docs`/`audit`/`spike`/`handoff` 卡不 bump、不产 artifact，`Release boundary` 写 `no-release` 并说明其产物随哪次发布进入用户渠道。任何多卡合并发布必须登记 `REL-*`。
- **G-08 家族卡:** 只有当变更确实无法切成可独立发布的切片时才用家族卡，且唯一发布点卡的 `Task type` 必须是 `release`。**本计划不使用家族卡**：REL-01 / REL-02 是串行窗口 + `no-release` 卡的 C 覆盖继承，承载点均为 `independent` 的普通发布卡。
- **G-09 拆分协议:** 拆分已被引用的卡时原编号保留给主轴，新子卡在所属 Phase 末尾追加编号，并同步全部交叉引用与「修订历史」。**本计划成稿后未发生卡拆分**（R1 修订为字段与判据订正，编号不变）。
- **G-10 写集与并发:** 每卡声明 `Implementation write set`（I）与 `Release write set`（R）。I–I 相交禁止并发且无豁免通道，只能补顺序边或合并到唯一集成卡；I–R 相交在串行发布窗口内由写锁处理；R–R 相交由 ER-12 的串行窗口顺序化。
- **G-11 任务类型:** 每卡声明 `Task type`。`audit`/`docs` 只读核对或文档收敛，规模上限按产物文件数或人日判定（`S` ≤ 5 个产物文件或 ≤ 0.5 人日；`M` ≤ 15 个产物文件或 ≤ 2 人日）；`spike` 不得改动生产代码；`release` 卡不引入新行为。

| 维度 | 切法 | 典型结果 |
|---|---|---|
| 数据 / 状态轴 | schema 扩展 → 写入幂等与持久化 → 读取投影与恢复 | 3 张卡 |
| 协议轴 | 协议版本与协商 → 容量 / 背压与性能门 → 消费端接入 | 3 张卡 |

| 清理轴 | 公开 surface 删除（家族卡） → 内部模块退场 → 依赖摘除 | 家族卡 + 普通卡 |

#### 粒度反模式速查

| 反模式 | 症状 | 处理 |
|---|---|---|
| 巨型卡 | `Estimated scope` = L；AC > 8；Description 含多个并列目标 | 按「推荐拆分维度」拆分（G-01/G-03/G-04） |

#### Verification 判定口径

- **零命中守卫必须区分「无命中」与「命令失败」。** `rg` 退出码 `0` = 有命中、`1` = 零命中、`>1` = 执行失败。`! rg …` 与 `if rg …; then exit 1; fi` 都会把 `>1` 误判为通过；裸 `rg …; rc=$?` 在 `set -e` 下也不行。统一使用下列模板：

  ```bash
  if rg -n "<pattern>" <paths>; then
    echo "FAIL: forbidden pattern found"; exit 1
  else
    rc=$?
    if [ "$rc" -ne 1 ]; then echo "ERROR: rg failed with exit $rc"; exit "$rc"; fi
    echo "OK: zero hits"
  fi
  ```

- 当被检查对象是**目录或文件是否存在**时，不得用内容检索代替存在性断言，必须用 `test -d` / `test -e` 并显式判定。
- 当零命中守卫的输入来自另一条命令时，必须先捕获该命令的输出与退出码并校验其成功，再把输出交给 `rg`；不得直接管道（管道会掩盖上游失败）。
- 「只允许 allowlist 命中」类守卫必须逐条比对固定 allowlist，并在任务记录中附命中 diff。
- 仅用于定位符号的 `rg` 必须注明「锚点定位用，非判据」。
- 本任务新增的 test fn / 场景过滤必须标 `(new)`，并确保其所属 `--test` target 已存在或在同卡内注册（`tests/compat/*` 还需 `Cargo.toml` `[[test]]`）并同步 `tests/INDEX.md`。
- `cargo test --all` 不能替代任务指定用例（ER-04）；指定用例也不能替代计划完成前的全量 L1 门。

  **补偿动作的统一幂等约定（G-01 要求的幂等键，全卡适用，卡内不重复）：**
  - **幂等键** = `revert(<TASK-ID>)@<被补偿的 forward commit 短 SHA>`，写在补偿提交 subject 里。它同时绑定任务与**具体目标提交**，因此同一张卡的第二次 forward 变更需要各自独立的补偿，不会被历史补偿误判为已完成。查重：`libra log --oneline | command grep -c "revert(<TASK-ID>)@<sha>"`，结果 ≥ 1 即跳过。
  - **前置状态判据（严格三态，逐路径判定；禁止二态简化）** = 该卡 forward 提交时必须为 `Implementation write set` 与 `Deliverables` 的**每一个具体路径**记录两组摘要并随任务记录留存：`PRE`（forward 之前的 sha256；当时不存在则记 `absent`）与 `POST`（forward 之后的 sha256；被删除则记 `absent`）。补偿前逐路径计算 `NOW` 并判定：
    - 全部 `NOW == PRE` → **已完成**，整体 no-op，不产生任何提交；
    - 全部 `NOW == POST` → **可补偿**，按依赖逆序恢复**全部**路径；
    - 其余任何组合（含部分匹配）→ **冲突**，立即停止并升级人工核对，禁止覆盖或删除。

    「仅凭 `NOW != POST` 即判为已完成」是被明确禁止的二态判据。禁止无条件 `rm`/`rm -rf <目录>` 做补偿——目录可能已含其它卡的产物（例如 `tests/compat-ledger/t4/` 同时被 CT3-01 与 CT3-02 写入）。
  - **重复执行判据** = 补偿脚本按具名路径覆盖写或删除，可重复运行；再次运行时三态判定会落到「已完成」并 no-op。`libra commit` 在无差异时失败退出，同样视为「已完成」而非错误。
  - **验证命令** = 补偿推送后 `libra rev-parse origin/main` 与本地一致，且该卡的 focused 用例回到变更前的预期结果。
  - **发布卡额外说明**：已推送的 tag 与已上传的 R2 产物**不撤回**（`immutable-release` 语义的部分），补偿靠更高的 patch 版本 + 新 tag；用户影响 = 中间版本存在一次行为变化，降级指引写在补偿提交的 CHANGELOG 条目中。

### Task CT1-02: `update-ref` 的值操作数接受 revision 表达式

**Task type:** `implementation`（G-11）

**Lifecycle / Acceptance:** `pending` / 空（2026-07-29：`DEP-04` 已解除，阻塞已撤销）（ER-04）

**Description:** 让 `libra update-ref refs/heads/<name> <newvalue> [<oldvalue>]` 的**值操作数**经既有 revision 解析引擎解析，且**不做隐式 peel**。对象类型校验**只作用于 `<newvalue>`**：其解析结果本身必须是 commit，否则拒绝（与 Git 一致：lightweight tag 可用、bare annotated tag 被拒、显式 `<tag>^{commit}` 可用）；`<oldvalue>` 只解析为原始 OID 参与精确比较，**不施加任何对象类型限制**。`<ref>` 操作数仍限定 `refs/heads/*` 的既有收窄。本卡唯一的行为轴是**值操作数的解析入口**。

**Out of scope:**

- 放宽 `<ref>` 操作数的命名空间——永久非目标，`COMPATIBILITY.md:180` 已声明为有意收窄。
- `--stdin` 批处理与 `--no-deref`——尚未排期，重启条件：出现具体迁移场景需求。
- 改动分支保护 / 归档策略的位置或语义——永久非目标；`LBR-POLICY-001` 的 fail-closed 与事务边界不变，本卡只保证其不被新解析路径绕过。

**Current evidence:**

### 任务卡粒度审计表

**计数口径（可机械复算）**：本计划的每张卡都已把 `Acceptance criteria` 写成**逐条原子谓词**——任一 checklist 行内不含 `且`/`并且`/`以及`/`同时` 连接的可分别失败的断言，也不含嵌套子列表或表格行。因此 **AC 分子 = 该卡 `Acceptance criteria` 小节的 `- [ ]` 行数**，`VER` 分子 = `Verification` 小节的 `- [ ]` 行数**减去** ER-04 的强制门（`install.sh` 的 `bash -n` / 冒烟表面门）。

**关于「取证手段的枚举是否计入 AC」**（此前评审轮反复出现的分歧，在此定死口径）：模板 G-03 的计数对象是 `Acceptance criteria` 小节中的**断言**，其展开规则只有三条——`且`/`并且`/`以及`/`同时` 连接的可分别失败断言、**嵌套子列表**、**表格行**。「一条 AC 由 N 个具名用例 / N 个反例 fixture / N 个记录字段取证」属于**取证手段**（`Verification` 的职责），不是 N 条独立 AC；否则任何「某守卫生效」类 AC 都会随其测试用例数线性膨胀，模板给 implementation 卡的 8 条上限将无卡可满足。为消除歧义，本计划已把此前写在 AC 里的「由 N 个用例逐个固定」「每个反例 fixture」「符合 N 字段规格」等**外引枚举钩子全部删除**，AC 只留单主语单断言的行为陈述，枚举明细留在 `Verification` 与各自的规格小节。

**若仍判定某张 implementation 卡超限**：按模板，`G-03 条目上限` 的 waiver 白名单只覆盖「清单型产物（文档 / 审计 / 索引）」，implementation 卡不可豁免，唯一出路是拆卡。但拆分方案必须同时满足 G-01（每张子卡是一个**可独立恢复、可独立发布**的行为轴）与 G-02（**禁止**拆成「实现卡 / 补测试卡 / 补文档卡」）。据此，「把守卫与其反例 fixture 拆开」「把新增行为与其无回归断言拆开」都不是合法拆法——它们会产出一张不含任何行为变更的卡。提出拆卡意见时请一并给出满足 G-01 + G-02 的具体子卡边界。
